# Devices tab

The Devices tab (`Ribbon`, alongside **Run** and **Layout**) swaps the main
content area for `DevicesGrid`
([lib/devices/devicesgrid.h](../lib/devices/devicesgrid.h)) instead of the
dashboard canvas (`DashboardGrid`) — `MainWindow` holds both inside a
`QStackedWidget` and switches which one is current on tab change
(`MainWindow::onRibbonTabChanged`, `lib/core/mainwindow.cpp`). The
layers/properties panels stay hidden here exactly as they already do outside
the Layout tab (`updatePanelVisibility()` gates them on
`m_configureTabActive`, which is only ever true for Layout).

## Pieces

- **`Device`** ([lib/devices/device.h](../lib/devices/device.h)) — one
  connected/known device: `id` (stable identity, auto-generated by
  `DevicesGrid::addDevice()` if left empty), `name`, `connected` (live-
  mirrored from its `DeviceConnection`, not user-editable), `commType` (a
  `CommType` enum — only `CommType::Btp` exists today), `description`,
  `portName`/`baudRate`/`lineTerminator` (the real transport config a
  `DeviceConnection` opens with), plus `btpVersion`/`chipType`/`btpId`
  standing in for whatever a real device manifest will eventually report.
  Plain public fields, same low-ceremony value-type style as
  `DashboardItem`. `deviceToJson()`/`deviceFromJson()` (same file) persist
  everything except `connected` -- see "Persistence" below.
- **`DeviceCard`** ([lib/devices/devicecard.h](../lib/devices/devicecard.h))
  — one device's card, fixed size (`kDeviceCardSize`, 260x140), painted in
  the same procedural-`QPainter` chrome style as `DashboardCell`'s header
  (icon, connection-status dot, gear button) but far simpler: it never
  moves or resizes once placed. A plain click selects it (accent-colored
  border, single-selection only — no Ctrl-click multi-select); the gear
  only emits `configRequested(deviceId)`, a plain click only emits
  `selectRequested(deviceId)` — neither opens anything or flips the
  selection state itself, `DevicesGrid` owns both.
- **`DevicesGrid`** ([lib/devices/devicesgrid.h](../lib/devices/devicesgrid.h))
  — owns the list of devices and their cards, and is the only public
  surface a caller needs: `addDevice()`, `removeDevice()`,
  `updateDevice()`, `devices()`, `selectedCount()`, `removeSelected()`.
  Also owns opening `DeviceConfigDialog` in response to a card's
  `configRequested()` and turning `selectRequested()` into an actual
  selection change (deselecting whatever card was selected before) —
  callers never construct or reference `DeviceConfigDialog` directly, and
  never touch a card's selection state directly either.
- **`DeviceConfigDialog`**
  ([lib/devices/deviceconfigdialog.h](../lib/devices/deviceconfigdialog.h))
  — edits one `Device`: name/description, a "Connection" section (port
  combo + refresh, baud, line terminator -- the config a `DeviceConnection`
  actually opens with) plus a read-only status line, and a read-back
  "reported by device" section (`btpVersion`/`chipType`/`btpId`). Opened
  and applied entirely inside `DevicesGrid`; accepting it calls
  `updateDevice()` on the grid's own copy. `DevicesGrid` can't enumerate
  serial ports itself (`traceview_devices` doesn't depend on `QSerialPort`,
  see `lib/CMakeLists.txt`), so it takes a port-list provider callback
  (`DevicesGrid::setPortListProvider()`, supplied by `MainWindow`) and
  forwards it into the dialog's `setAvailablePorts()`/`refreshPortsRequested()`.

## Connections

Real per-device transport now lives in **`DeviceConnection`**
([lib/core/deviceconnection.h](../lib/core/deviceconnection.h)) --
`traceview_ui`, not `traceview_devices` (see the layering note above): each
`Device` gets its own `SerialManager` (raw bytes) plus `Backend` (protocol
decode/encode, concretely a `BtpBackend`), so several devices can be open at
once, each running its own independent BTP session. `MainWindow` owns a
`QHash<QString, DeviceConnection*>` keyed by `Device::id`, built and torn
down in lockstep with `DevicesGrid`'s own list
(`DevicesGrid::deviceAdded`/`deviceRemoved`/`deviceUpdated`).

Connecting is **ambient**, not a one-shot action: `DeviceConnection::connectTo()`
records intent ("this device should be online at this port/baud") separately
from whatever `SerialManager::isConnected()` currently reports, and a timer
retries `open()` every few seconds while the two disagree -- covers both a
freshly configured device's first connection attempt and silently recovering
from an unplug/replug, with no user action needed either time. A device with
an empty `portName` is simply "not configured" and never attempts to open.
`disconnectFrom()` (or the status dot's connect-toggle click, see below) is
the only thing that turns the intent back off.

**Per-widget device targeting**: every dashboard widget kind that talks to a
device (chart, gauge, push button/toggle/slider, serial monitor) has its own
"Device" picker in its config editor, storing the chosen `Device::id` as
`deviceId` in that widget's JSON config -- there is no single "active
device," each widget picks its own. `WidgetConfigEditor::setAvailableDevices()`
(`lib/dashboard/widgetconfigeditor.h`) is how each editor gets the current
device list to populate that combo from (pushed by `PropertiesPanel`, fed by
`MainWindow` converting `DevicesGrid::devices()` into the tiny local
`DeviceOption` value type -- `traceview_dashboard` doesn't depend on
`traceview_devices` either, same layering reason as above).

At runtime, `MainWindow` resolves each chart/gauge widget's subscription
against its *own* device's `Backend` (re-pointing it if the widget's
`deviceId` changes), and `SerialWidgetBridge`
([lib/core/serialwidgetbridge.h](../lib/core/serialwidgetbridge.h)) does the
same for control-widget commands and the serial monitor's TERMINAL_IN/OUT --
resolving the target `DeviceConnection` fresh on every outbound send, and
re-pointing the terminal's inbound connection when its device changes.
Each dashboard cell's header status dot reflects *its own* configured
device's connection state (`DashboardGrid::setDeviceConnected(deviceId, bool)`),
not a single global flag. A widget with no device chosen (or an old saved
layout predating this field) shows as disconnected and generates no wire
traffic, the same "unconfigured means inert" contract `sourceId`/`topicId`
already had.

The Run ribbon tab no longer hosts a port/baud/connect bar (that's per-device
now, in the Devices tab) -- instead it shows a read-only strip of every
configured device's name and connection dot, for an at-a-glance summary that
doesn't require switching tabs or having any dashboard widget bound to that
device.

## Persistence

Devices are saved into `.tvproj` under a top-level `"devices"` section
(`ProjectStore::setSection("devices", ...)`), written by
`DevicesGrid::toJson()` and restored by `DevicesGrid::fromJson()` (which
replaces the current list rather than merging, same contract as
`DashboardGrid::fromJson()`). `connected` is deliberately not persisted --
it's live transport state, not configuration; a freshly loaded device starts
disconnected and `DeviceConnection`'s ambient retry takes it from there if a
`portName` is set.

## Layout

Unlike the dashboard canvas, a `DeviceCard` is never dragged, resized, or
manually repositioned. `DevicesGrid` auto-flows cards left-to-right,
top-to-bottom, wrapping based on available width — display order is simply
insertion order (`row = index / itemsPerRow`, `col = index % itemsPerRow`),
recomputed on every resize and on every add/remove. There's no occupancy
scan or free-slot search the way `DashboardGrid::findFreeSlot()` does for
draggable items, because there's no notion of a "hole": `removeDevice()`
always compacts, re-flowing every following card into the gap left behind.
Gutter spacing mirrors `DashboardGrid::gutter()`'s scale (a fraction of the
panel's shorter side, clamped to the same min/max) purely for visual
consistency between the two grids — `DevicesGrid` doesn't depend on the
dashboard library to get it.

## Adding / editing / removing a device

The Devices tab's ribbon page has two buttons, **Add Device** and **Remove
Device**, mirroring the Layout tab's own **Add**/**Remove** pair.

**Add Device** (`MainWindow::onAddDevice`) appends a placeholder `Device`
(name `"New Device"`) via `DevicesGrid::addDevice()` — no picker dialog,
same shape as the dashboard's own **Add Widget**. The new card shows up
with a placeholder name; clicking its gear opens `DeviceConfigDialog` to
rename it or edit its other fields. There's no separate "add and
immediately open config" path — `DevicesGrid`'s public API doesn't expose
one, and a plain add-with-placeholder is enough for this pass.

**Remove Device** (`Delete` shortcut, gated on the Devices tab being active
— see `MainWindow::updateDeviceSelectionActions()`) calls
`DevicesGrid::removeSelected()` for whichever card was last clicked. A
plain click on a card selects it (single-selection only, no Ctrl-click);
clicking a different card replaces the selection rather than adding to it.

## Current scope

Devices are added by hand via **Add Device** (there's no discovery/scan
picker) and each one is a real, independent BTP connection once given a
port -- see "Connections" above. `btpVersion`/`chipType`/`btpId` are still
plain editable text in `DeviceConfigDialog`, not populated from a live
device: wiring those up to a real BTP manifest exchange (`ManifestClient`,
see [docs/PROTOCOL.md](PROTOCOL.md)) is later work.
`DevicesGrid`/`DeviceCard`/`DeviceConfigDialog` themselves still have no
dependency on `lib/protocol/` or `SerialManager` -- that stays true by
design (see the layering note above); the real transport wiring lives in
`traceview_ui` (`DeviceConnection`/`MainWindow`), not inside the devices
module itself.
